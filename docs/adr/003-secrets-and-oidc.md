# ADR 003: RDS owns the password, GitHub uses OIDC

Status: Accepted
Date: 27 October 2026

## Context

The previous database password was a Terraform variable. That puts the secret in state and invites it into a tfvars file. The task also received `DATABASE_URL` from the whole Secrets Manager secret, which is JSON, not a URL. CI was written to use a stored AWS key, and the OIDC trust allowed `repo:org/repo:*`.

## Decision

RDS sets `manage_master_user_password = true`. The master password is generated by RDS and stored in Secrets Manager under the workload key. The execution role may read that secret and decrypt with that key. The task receives `DB_USERNAME` and `DB_PASSWORD` as `secret_arn:json_key::`, plus host, port, name and `sslmode=require` as plain environment variables. There is no password variable.

GitHub Actions assumes roles through the token OIDC provider. The plan role trusts `repo:OWNER/REPO:pull_request` and `repo:OWNER/REPO:ref:refs/heads/main`. Each apply role trusts `repo:OWNER/REPO:environment:NAME`. The workflow grants `id-token: write` only on the plan and apply jobs. Fork pull requests are not allowed to assume the plan role.

Both roles deny `iam:CreateUser`, `iam:CreateAccessKey` and `ec2:RunInstances`. PassRole is limited to roles this stack creates for ECS, RDS monitoring and VPC flow logs.

This repository was created on 19 June 2026, before GitHub's immutable subject-claim change on 15 July 2026. The trust policy uses the classic `repo:Charles-dotcom/aws-cloud-engineer-portfolio:...` form. If the repository is opted into immutable claims, the subject becomes `repo:Charles-dotcom@80262628/aws-cloud-engineer-portfolio@1274291282:...` and the trust policy must change before CI can assume the role. Confirm the claim in a sample token before the first apply.

The GitHub thumbprint on the OIDC provider is `6938fd4d98bab03faadb97b34396831e3780aea1`. AWS has ignored GitHub thumbprints since 13 July 2023. The API still requires a value.

## Consequences

`terraform plan` reads state and writes the lock. It does not save state. The plan role can `s3:GetObject` on `environments/*` and `PutItem`/`DeleteItem` on the lock table. It cannot `s3:PutObject` or `s3:DeleteObject` on the state bucket, so a pull request cannot delete state or its versions.

Each apply role writes only `environments/<name>/` in the state bucket. Workload resources are named `{project}-{environment}-*`, and deletes of RDS, the load balancer, ECS, logs and the workload key require the `Environment` tag. The dev role has no prod ARN. `iam:CreateRole`, `PutRolePolicy` and `AttachRolePolicy` require the workload permissions boundary, and `AttachRolePolicy` may only attach `AmazonECSTaskExecutionRolePolicy` or `AmazonRDSEnhancedMonitoringRole`. An explicit deny blocks `iam:*` on `portfolio-gha-*` and on the GitHub OIDC provider. Apply does not manage that provider. Bootstrap, run locally, does.

Delete, revoke, modify, disassociate, detach and route changes require `aws:ResourceTag/Environment`. Creates require `aws:RequestTag/Environment` through TagSpecifications, and every taggable VPC resource carries that tag. A dev apply cannot change a prod network, database, load balancer or the state key. Tests: `dev_apply_is_scoped`, `single_nat_for_two_zones`, `rejects_a_missing_environment_tag_deny`.

The RDS master-user secret in state contains `secret_arn`, `kms_key_id` and `secret_status`. It does not contain the password. The password stays in Secrets Manager.

Apply permissions are customer managed policies, at most 10 per role and 6144 non-whitespace characters each. Inline policies stay under 10240. Tests: `dev_apply_is_scoped`, `rejects_an_oversized_document`. The state key ARN is unknown on the first bootstrap plan only. Separate accounts per environment would isolate dev from prod further; this repository does not build that.
